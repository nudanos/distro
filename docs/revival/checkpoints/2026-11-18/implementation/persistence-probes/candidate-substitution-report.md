# Candidate substitution prerequisite probe

2026-11-17–18. This is a bounded diagnostic, not a password-persistence pass. The source `candidate-substitution.py` accepts a private password file and fixture username externally; it does not contain a credential. A random candidate password was generated inside the disposable appliance and removed after the probe. No password or actual encrypted hash was printed.

Native Windows QEMU/WHPX booted a new writable child `test-runtime/acceptance-persistence-probe/probe.qcow2` of the read-only `acceptance-interim/persistence-failure.qcow2` (itself backed by the read-only baseline master). QMP was bound to `127.0.0.1:18774` and SSH forwarding to `127.0.0.1:2230`; a temporary HTTP server at `127.0.0.1:18775` served the credential-free source. The VM was shut down and that server stopped after probing. The child disk passed `qemu-img check`; the preserved failure and baseline files still matched their respective SHA-256 values `749dd674a08943f030c0f8a88a547ed13f5f7eb38067a58b05f15c2896a6e548` and `823195ac55359ea2b0f1e11433c6d2a3d8953811c1c44b70f1be813e1295a9dd`.

From a normal serial login as the existing fixture superuser, sudo ran the probe under the inherited audit login identity. The probe created a unique private configd session, called `set` on target `renew`'s plaintext-password, requested the CANDIDATE encrypted-password, and tore down the session without commit. `set` returned and the encrypted-password field was present, but its returned value was the redaction mask. The RUNNING secret was also masked, so the actual substituted hash and actual running secret cannot be verified from this client context. The target shadow-entry SHA-256, `/config/config.boot` SHA-256, and canonical fingerprint of the redacted RUNNING `system login` tree were identical before and after teardown. Equality of a redacted tree is not proof that unmasked secrets are equal. Serial transcript: `test-runtime/acceptance-persistence-probe/boot.log`. The final probe source SHA-256 is `97e93cd1b2664c9c76c337db18aefced45a59f50b9f4d699ad2d321ed21a6740`.

Read-only inspection showed sudo's child audit loginuid was 1017 (the fixture superuser). The actual provisiond process ran with UID/EUID/GID/EGID 0 and audit loginuid 114, corresponding to `configd`; `configd` belonged to the configured `secrets` group. Both password leaves are marked `configd:secret` in the YANG model. Source inspection by the root agent found substitution executes synchronously inside configd's set path before it returns, but this probe did not observe an unmasked usable candidate hash in the production helper context.

An attempted subprocess audit-loginuid change was rejected by automatic approval review as an unauthorized security-relevant attribution change. It was not retried or bypassed. Normal authorized VCI password renewal through provisiond is the appropriate later end-to-end check of production identity and persistence.

**Historical note (November 18): the following proposed test depended on a false assumption about public configd Commit and is superseded. It is retained only as the original diagnostic context.**

The later integration test should deliberately create an unrelated committed-but-unsaved API change, perform actual password renewal, and immediately reboot without any intervening CLI commit or save. Verify the changed password survives, the unrelated unsaved change does not become persisted, other accounts and administrator-owned PAM state remain intact, and configd/session and disk fingerprints are recorded around each boundary.
