# Password persistence: disposable appliance diagnostics

2026-11-18. These are bounded tests on a disposable child of the preserved interim appliance, not final-image acceptance. Credentials were supplied through private runtime files or suppressed serial entry; this report contains no credentials, raw password hashes, raw serial logs or private snapshots.

## Fixture and earlier prerequisite

The appliance began from the preserved interim failure snapshot, with configd 2.17 and login/YANG 2.45. Running configd was active and its executable matched the installed binary, SHA-256 `8001be84bb8a7280d8e91fbf74c46e948c885005e987c08d5a18fea19007ec76`. A private API commit of a benign domain-name marker unexpectedly updated startup configuration; source inspection confirms this configd's successful public Commit calls Save. Thus it was a **saved** baseline marker, not an unrelated committed-unsaved fixture. No test below claims coverage of an unsaved committed change. The marker was present before each password test, and no later CLI commit or save was performed before its associated reboot.

## Original 2.45 RPC

The guest-only observer delegated to the exact saved original RPC, SHA-256 `90aded4e6877594cf309043cab47aff573e18574e9b5675f69b71e909e8b39aa`, preserving stdin, arguments, environment and service identity. It logged only entry/exit, commit-result classification and length. The actual PAM stack selected `pam_vyatta_passwd.so`; a normal in-session SSH/PAM `passwd` conversation returned success. The observer recorded verify and change RPC exits of zero, with a zero-length commit result and no nonfatal-warning classification. An exact comparator found that only the target user's saved encrypted-password value changed; all other startup-file bytes were identical. After immediate clean guest reboot shutdown and same-disk cold boot, the prior password was authentication-rejected and the new password accepted.

The distinct expired pre-session SSH/PAM path was then exercised after expiring only the target account, retaining a separate recovery-superuser session. It also returned success, recorded zero-length/nonfatal-false commit and RPC exits of zero, and passed the same target-only saved-byte comparison. Following immediate clean guest reboot shutdown and same-disk cold boot, the prior password was rejected and the new one accepted. No CLI commit or save intervened. The earlier historical pre-reboot failure remains preserved, but its persistence outcome was **not reproduced** by these controlled original normal and expired SSH paths; these tests do not establish its cause.

## Exact CI-built 2.46 package

Installed `vyatta-login_2.46_amd64.deb`, SHA-256 `4cf0547b5031a6f81cacc480affda68313fd184bfdacbed2682bd0a84e9e95c3`, in the disposable guest. `dpkg -i` exited zero and `dpkg --audit` was clean. Package entries were root-owned RPC mode 755 and helper mode 644. Installed RPC SHA-256 `00df845f5f52e2b336a686d70e9744b278192bf5939112da6e05022e9e58c7bd` and helper SHA-256 `316940c19f571c2553f5f4baae7463bf54bea637c7b900a585a768e812335d64` matched the reviewed CI source. Installation replaced the temporary observer with the production RPC.

Both the real normal in-session and expired pre-session SSH/PAM password conversations completed successfully using private credentials. For each, the saved-byte comparator confirmed the target password changed and all other startup-file bytes remained identical. Each was followed immediately by clean guest reboot shutdown and same-disk cold boot, without an intervening CLI commit or save; in each case the preceding password was authentication-rejected and the new password accepted after system configuration became active. These are live package diagnostics with the existing 2.17/2.45 companion cohort, not full final-image, serial pre-session, fresh-install, or full-upgrade acceptance.

## Synthetic end-hook failure control

On a separate child of the passing 2.46 fixture, a temporary test-only updater wrapper delegated `--validate` unchanged, ran the real `--system` updater, then emitted a fixed diagnostic marker and exited 42. The real SSH/PAM password conversation returned exit 10 with RPC/token-failure classification; it did **not** report success. Startup configuration remained byte-identical to its pre-test snapshot. Before reboot, the prior credential was rejected and the newly attempted one accepted, demonstrating **active runtime** state changed while the saved state remained old; this is not a persisted-password pass. Configd's journal identified the synthetic end-hook failure under `/system/login`. The exact original updater was restored immediately, and its SHA-256 `c8e16712d3ae30e8406aa4f867a417765476ff0a6e13de7d5f0dd50f9f944632` matched its pre-injection value. The wrapper was confined to this disposable guest and is not part of a product package.

## Reboot and preservation limits

On these tests `systemctl reboot` reached the guest's `reboot: Restarting system` after shutdown, but QEMU/WHPX paused with VP exit code 4 during the hypervisor restart. The paused VM was identity-checked through QMP, closed, and the same disk cold-booted. This is evidence of clean guest shutdown plus same-disk cold boot, not a successful in-process WHPX reboot. Local QEMU help confirms `-no-reboot` exits instead of rebooting; it was added to subsequent launches, but it did not apply to the already-run reboot observations above.

All diagnostic VMs were stopped. The synthetic failure child passed `qemu-img check` and was marked read-only; its SHA-256 is `7c5c1a67a7613176edd19f7b6c16eaf1ec64232df5244e7dbf48b4341f57a510`. Its read-only passing parent remains `6cc6454b9c4e384d2eeaa23d6230bc916d5cfe05687296c8550426ed317029cb`; the prior interim failure snapshot and baseline master still match `749dd674a08943f030c0f8a88a547ed13f5f7eb38067a58b05f15c2896a6e548` and `823195ac55359ea2b0f1e11433c6d2a3d8953811c1c44b70f1be813e1295a9dd`. Runtime credential files and raw logs are local test material and are not part of the report or package.
